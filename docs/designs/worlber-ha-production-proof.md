## Problem Statement
Patroni works and self-heals, but every node needs etcd and a hand-edited YAML
file, and the tooling for steering, failover and failback is often paid.
worlber_ha already gives the SQL Server Always On experience: managed from
psql, embedded Raft, no YAML (contrib/worlber_ha, versions 1.0 to 1.2). What it
lacks is **evidence that it is safe at production volume**. The only
data-loss proof today is one client writing 452 rows (testing/lab.sh:257-280).
In the user's words: "it will be working in high environments where people will
use it for production; if not stable it's dangerous."

## What Makes This Cool
The "pull the plug live" moment:
1. Ledger clients write thousands of TPS through the listener while long
   reports run on the replicas.
2. Someone kills the primary.
3. The clients reconnect and keep writing.
4. The harness compares every acknowledged write in the client-side ledger
   with the new primary and finds **zero acknowledged rows missing**.
5. `worlber_ha.verify_table()` then shows that every replica holds the same
   data as the new primary.

The proof then keeps running in production. `SELECT * FROM worlber_ha.proof`
shows:
- when the cluster was last proven;
- its canary-based RPO and drill-measured RTO;
- how many drills in a row passed.

We have not found published RTO/RPO measurements under load for Patroni or
pg_auto_failover (web search, 2026-10-13).

## Constraints
- B1: leave encryption alone (no TLS work).
- B2: everything stays at the psql level. No YAML, no external DCS.
- Workload: OLTP writes on the primary plus heavy read-only reporting on
  replicas (user answer Q2).
- Speed bar: conservative. Unplanned failover RTO p95 under 30s, never a
  false failover or split brain (user answer Q3).
- Open source / community project: anyone must be able to get it and
  reproduce the demo.

## Premises (all agreed)
1. Proof, not features. Build the load and chaos harness with measured
   RTO/RPO, then fix what breaks.
2. Long reports on replicas are a first-class test target: lag, recovery
   conflicts, cancelled queries, blocked redo.
3. Safe over fast. Unplanned failover under 30s; RPO 0 with a synchronous
   replica; never split brain or false failover; switchover in seconds.
4. Easy to get and reproduce. Published images/packages, a one-command demo,
   and per-node setup reduced to "install + join with a token". This design
   covers the images and the demo. "Install + join with a token" is
   **deferred to a follow-up design**, because premise 1 puts proof first.

## Cross-Model Perspective
Independent Claude subagent (Codex not installed), cold read:
- **Coolest version:** proof that never stops: an always-on RPO canary,
  `worlber_ha.drill('switchover')` under live traffic, and a failover receipt
  in `events`.
- **Key quote:** "verify_table() proves zero rows lost": the user wants the
  proof, not the failover.
- **50% exists:** pgbench, Pumba/toxiproxy/tc netem/iptables, and later Jepsen
  with its Elle checker. To build: an acknowledged-write ledger across N
  clients, an RTO clock, a report workload, a fault matrix with verdicts.
- **Code risks.** These three are confirmed by reading the code:
  - **Critical:** a primary whose agent died, or whose PostgreSQL hung and
    recovered, is never fenced. There is no watchdog (failover.go:116,166;
    router.go:303).
  - **High:** a crashed PostgreSQL reports LSN 0, which skips
    `maximum_lag_on_failover`, so a far-behind async standby can be promoted
    (pg.go:157, agent.go:402, failover.go:38).
  - **High:** `available` mode drops non-streaming sync nodes from
    `synchronous_standby_names`, while candidate ranking still trusts the
    configured sync flag. The node that was *actually* synchronous is never
    recorded (reconcile.go:257, failover.go:51).

  Not yet confirmed:
  - **Medium:** fencing can be starved by a blocked reconcile (reconcile.go:83).
  - **Medium:** there is no replica report policy (router.go:197-207).
  - **Low:** a single-probe health check (pg.go:150).

## Recommended Approach (B)

### 1. Chaos harness (`contrib/worlber_ha/testing/chaos/`, on the docker lab)
- **Ledger client:** `worlber-ledger`, a new Go program in the agent module.
  It runs N workers. Each worker:
  - inserts `(client, seq, ts)` in its own transaction through the
    read-write listener;
  - reconnects and retries on any connection error;
  - logs every attempt with one of three outcomes:
    - **acknowledged:** COMMIT returned OK;
    - **failed:** an error came back before COMMIT was sent;
    - **unknown:** the connection was lost after COMMIT was sent, or COMMIT
    returned with the warning "canceling wait for synchronous replication".
  Workers never cancel a pending COMMIT, so there is no statement_timeout and
  no client cancel request. A COMMIT still waiting after 15s has its socket
  closed and is logged as *unknown*.
  pgbench is used only for extra background throughput, never for the
  verdict.
- **Report workload:** sessions on the read-only port run 5-10 minute
  aggregates in a loop. Each one logs completed, cancelled, or routed-to.
- **Scenarios:**
  - S1: kill PostgreSQL on the primary (agent alive)
  - S2: kill the agent on the primary (PostgreSQL alive)
  - S3: `docker pause` the primary for 60s, then unpause
  - S4: iptables partition of the primary
  - S5: kill the sync standby, then the primary 5s later
  - S2b: blocked reconcile (debug flag) plus a partition of the primary
  - S6: kill the primary during a switchover
  - S7: 30 minutes of load with no faults
  - S8: long reports under load
- **Loss check:**
  - Only *acknowledged* rows count toward loss. Unknown rows are reported
    separately: they may or may not exist, and both are correct.
  - Divergence check: before the old primary rejoins, the harness stops its
    container, copies its data volume, and starts that copy in an isolated
    container (no network, `default_transaction_read_only=on`,
    `worlber_ha.fence=off`, so the fence worker does not shut it down). The
    harness waits until crash recovery has finished and the server accepts
    queries, then counts
    ledger rows that exist there but not on the new primary. Those must all be
    *unknown* or *failed*, never acknowledged.
  - Only then does the old node start and rejoin.
- **RTO:**
  - Per client: time from its last acknowledged commit before the fault to
    its first acknowledged commit after it, measured through the read-write
    listener (and through the VIP in S1/S4).
  - Per run: the maximum over all clients.
  - Lab matrix: 20 runs per fault scenario per TPS rung. The RTO p95 gate
    (nearest rank, the 19th of 20) applies to S1–S6 and S2b. S5b is gated on
    RPO only.
  - **Health timer:** the leader's failover timer starts at the last heartbeat
    reporting `Running=true`. The 3-probe rule only decides when the
    primary's agent reports `Running=false`.
  - S7: 3 runs × 30 min per rung. S8: 3 runs per rung. RTO does not apply
    to these two.
- **Verdict:** one JSON file per run with RTO, acknowledged-missing,
  unknown-count, divergent-acknowledged, false failovers, report
  cancellations, and max replay lag.

### 2. Fencing (the Critical fix)
- **Fence worker:** a background worker in the worlber_ha extension
  (shared_preload_libraries).
  - It enforces only when GUC `worlber_ha.fence = on`. The default is `off`,
    so standalone servers and servers without an agent are never fenced. The
    agent sets it to `on` with ALTER SYSTEM when the node joins a cluster;
    `worlber_ha.set_config('fencing', 'off')` turns it off cluster-wide for
    maintenance.
  - Propagation (R3-6): `worlber_ha.fence` is a SIGHUP GUC.
    - The `fencing` option is committed to Raft, and each agent applies it on
      its own node with ALTER SYSTEM + `pg_reload_conf()` during reconcile.
    - A node whose agent is down keeps its last value; "on" means it stays
      fenced, which is safe.
    - Turning fencing back on takes effect as each agent reconciles.
    - `health_check()` warns while any node has fencing off.
  - It acts only while the server is **not in recovery**. Standbys,
    including a rejoining old primary, are never fenced.
  - Every 500ms it checks the lease (below). When the lease is stale, it
    sends SIGINT (fast shutdown) to the postmaster. It runs as the postgres
    OS user and needs no extra privileges.
  - Write safety comes from the start of fast shutdown: backends are
    terminated and new connections are refused. The worker itself is ended by
    the postmaster during shutdown, so it does no escalation. Escalation to
    SIGKILL is done only by the agent's fencing goroutine, while the agent is
    alive.
- **Lease content, on a step-free clock:**
  - The agent writes `$PGDATA/worlber_ha.lease` atomically (write to a temp
    file, then rename) with `boot_id`, a `CLOCK_BOOTTIME` timestamp, Raft
    term and epoch.
  - The lease timestamp is the `CLOCK_BOOTTIME` value read when the renewal conditions were last verified, not when the file is written. If more than 200ms pass between that check and the rename, the write is discarded and the check is repeated.
  - The worker compares that timestamp with its own `CLOCK_BOOTTIME`. This is
    the same host and the same boot, and the clock is not affected by NTP or
    manual steps and keeps counting through suspend and docker pause.
  - The lease is stale if it is older than `lease_ttl`, if its timestamp is
    in the future, or if `boot_id` differs.
  - If the file is absent, the worker allows `lease_ttl` after postmaster
    start, then treats the lease as stale.
- **When the agent renews.** Every 1s, but only when all of these hold:
  - the FSM says this node is primary for the current epoch;
  - **quorum is confirmed within `Q = 2s`**:
    - as Raft leader: a successful `VerifyLeader()` within the last 1s;
    - as follower: a heartbeat to the leader acknowledged in the current
      term and sent within the last 2s, plus a `/peer/info` confirmation of
      primary + epoch within the last 2s.
      Each follower measures its window from the moment it **sent** the heartbeat that the leader later acknowledged, not from when it received the acknowledgement. Every heartbeat the leader receives was sent earlier, so in real time a follower renews for at most Q after the leader's last received heartbeat. Both durations are measured on local monotonic clocks, whose rate drift (well under 0.1%) is absorbed by the 2s margin. A new Raft leader starts its failover timer at the later of the last heartbeat it received from the primary and the moment it became leader. It may never have seen the old primary's heartbeats, and this keeps the bound valid.
  - no monotonic-clock gap above 2s between agent ticks since the last
    reconfirmation.

  Consequence: after the leader's last received heartbeat, the primary can
  renew for at most `Q` more. Its PostgreSQL stops accepting writes by
  `Q + lease_ttl + 0.5s` (check interval).
- **Lifecycle ordering:**
  - **Promote / start as primary:** the agent writes a fresh lease *before*
    `pg_promote()` or `pg_ctl start`, so a newly promoted node is never
    fenced.
  - **Pause mode:** renewal continues (pause disables automatic actions, not
    fencing).
  - **Planned agent restart:** it must complete within `lease_ttl` or the
    primary fences itself. This is documented; set `fencing` to `off` first
    for slow maintenance.
  - **Bootstrap (`create_cluster`):** the lease is written first, then
    `worlber_ha.fence=on` is set.
- **S3 (docker pause, then unpause):**
  1. Everything freezes. On unpause, the agent sees a monotonic gap above 2s
     and stops renewing. It changes nothing in PostgreSQL: no
     `synchronous_standby_names` change, no VIP add, no read-write routing.
     It first drops the VIP, then waits until it has reconfirmed quorum and
     its role in the current term.
  2. The fence worker's first check sees the stale lease, because it is
     already past `lease_ttl` measured on `CLOCK_BOOTTIME`, and stops
     PostgreSQL.
  3. Direct connections in the ≤500ms window can only end *unknown*. With
     `synchronous_commit=on` their COMMITs block, because the sync standby now
     follows the new primary.
  4. Expected: 0 acknowledged rows on the old primary that are missing on the
     new one.
- **Agent-side fencing goroutine (unconditional):** fencing inside the agent
  moves to its own goroutine with a hard deadline and a SIGKILL fallback; it
  is the only component that escalates to SIGKILL. Scenario **S2b** (a
  blocked reconcile injected through a debug-only flag, plus a partition)
  proves fencing still happens.
- **VIP when the agent is dead:**
  - The fence worker cannot remove the VIP (no NET_ADMIN), and we accept
    that. Safety comes from PostgreSQL being stopped by the lease, plus the
    new primary's gratuitous-ARP takeover. A stale VIP on a node whose
    PostgreSQL is down accepts no writes.
  - This is documented as a known trade-off.
- **softdog:** not used. `/dev/watchdog` is host-wide and would reboot the
  shared docker lab and the CI runner. It may be added later as an optional
  production add-on; out of scope.
- **Timing budget**, with `failover_timeout` lowered from 30s to **20s** and
  `lease_ttl = 7s`:
  - The old primary stops accepting writes by Q (2s) + lease_ttl (7s) + 0.5s
    = 9.5s after the leader's last received heartbeat.
  - The leader commits a failover only after `failover_timeout` (20s) since
    that heartbeat, measured on its local monotonic clock. 20s ≥ 9.5s + 2s
    margin.
  - The bound `failover_timeout ≥ Q + lease_ttl + 0.5s + 2s` holds for any
    timeout ≥ 7s, with `lease_ttl = failover_timeout / 3` and Q fixed at 2s.
  - **Gate and fallback (R3-9):** S7 and S8 gate the 20s default. If false
    failovers appear, the default falls back to `failover_timeout = 30s`
    (`lease_ttl` 10s); the bound still holds.
  - **Health probe (R3-8):** the primary counts as unhealthy only after 3
    consecutive failed probes (1s apart), not a single 3s probe. S7 gates
    this. Confirmation from the standby side (its WAL receiver lost the
    primary) is deferred.
  - Budget: detection 20s + promotion ~2s + client reconnect ~3s ≈ 25s,
    which is under the 30s p95 bar.

### 3. Promotion safety (the High fixes)
- **Last good LSN:** heartbeats keep the last good LSN and its timestamp. A
  Running=false heartbeat no longer overwrites it.
- **Actual sync node:**
  - The primary's agent reports which standby is actually synchronous right
    now (`pg_stat_replication.sync_state = 'sync'`).
  - `synchronous_standby_names` changes from `ANY 1 (...)` to `FIRST 1 (...)`, so exactly one standby is in `sync` state at any time; the others are `potential`. `actual_sync` is that single node. Automatic failover promotes only that node, or a reachable standby whose last good LSN is at least that node's last good LSN.
  - Changes are committed to Raft (`actual_sync`) in a safe order:
    - **Removing** a node: the new `actual_sync` without it is committed to
      Raft *before* the primary removes it from `synchronous_standby_names`.
      Until that commit succeeds, the primary keeps waiting for it, so
      commits block rather than being acknowledged without it.
    - **Adding** a node: it goes into `synchronous_standby_names` first, and
      is committed to `actual_sync` only after it reports `sync`.
  - Scenario S5b kills the primary immediately after the sync standby
    disconnects, to test this ordering.
- **New option `async_failover`:** `never` (default) or `within_lag`.
  - `never`: if `actual_sync` was empty when the primary was lost (S5), the
    cluster does not promote automatically. It records `failover_blocked`
    with the reason and waits for `worlber_ha.failover(force => true)`.
  - `within_lag`: an async standby may be promoted only if its last good LSN
    is within `maximum_lag_on_failover` of the primary's last good LSN.
  - Expected S5 result: no automatic promotion, the event explains why, and
    a forced failover records the estimated loss.
- **Commit level:** RPO 0 is claimed only with `synchronous_commit=on` (WAL
  flushed on the sync standby). `remote_apply` is not required.

### 4. Live proof
- **Canary:**
  - The leader's agent updates **one row**,
    `worlber_ha_internal.canary(id=1, seq, ts)`, through the primary every second with
    `synchronous_commit=on`. That is about 1 small WAL record per second.
  - Every agent reads the replayed `seq` locally.
  - Location: the `postgres` database, table `worlber_ha_internal.canary`,
    created by the agent.
  - The write runs in its own goroutine with a 5s deadline. On timeout it
    closes the socket and never cancels; while it is blocked, `canary_lag_s`
    is reported as unknown.
  - With no sync standby in `available` mode, the write is asynchronous and
    `worlber_ha.proof` marks RPO as "unprotected".
- **`worlber_ha.proof` view.** This is the single proof surface;
  `cluster_status` is unchanged. Columns:
  - `last_proven_at`: last successful drill
  - `last_drill_kind`
  - `last_drill_rto_s`
  - `last_drill_canary_lost` (seqs acknowledged but missing after the drill)
  - `drill_pass_streak`
  - `canary_seq` (primary)
  - `canary_lag_s` per replica (as rows: `node`, `canary_seq`, `canary_lag_s`)
- **Failover receipt** in `events` for every failover. The fields are things
  the cluster can observe; there is no application-row field:
  - `canary_last_acked_seq` vs `canary_seq_on_new_primary`
  - `primary_last_flush_lsn` vs `promoted_lsn`
  - `actual_sync_at_loss`
  - `fence_confirmed`, true when the lease had expired before promotion
- **`worlber_ha.drill(kind)`.** Privilege: `worlber_ha_admin`.
  - `switchover`: the existing switchover, then a switchover back.
  - `failover`: simulates the death of the primary node.
    1. The leader sends `drill_fence` to the primary's agent. That agent
       stops lease renewal and heartbeats, stops PostgreSQL with
       `-m immediate`, and stays silent.
    2. The leader runs the **unchanged automatic path**: detection after
       `failover_timeout`, then promotion of the `actual_sync` node.
    3. The measured drill RTO is therefore the real unplanned RTO: detection
       + promotion + client reconnect.
    4. After promotion, the old agent resumes and its node rejoins as a
       standby. The drill then switches back.
    5. While silent, the old agent sends nothing to the leader, but it still receives the Raft log and still serves its peer API. It learns the outcome from its own FSM: an epoch change with a new primary means it rejoins as a standby. An abort reaches it as a `drill_abort` peer call from the leader. If neither happens within 120s, it ends the silence by itself, reconfirms its role with the leader, and follows the FSM. Before restarting as primary after an abort, the old agent confirms with a quorum read (leader `/peer/info` after a Raft barrier) that the epoch is unchanged and no `set_primary` was committed. Only then does it write a lease under the normal renewal conditions. If the primary's agent is itself the Raft leader, `drill()` first transfers leadership to another member.
  - Preconditions (otherwise it refuses with the reason):
    - all members healthy, quorum intact, not paused;
    - the `actual_sync` node streaming synchronously (flush lag 0) with
      replay lag under 1s for 5s, which is achievable at the lab TPS rungs and
      verified in S7;
    - no failover or switchover in the last 10 minutes.
  - Abort. "The hold" is the existing switchover hold: the old primary's
    agent does not restart PostgreSQL as primary while it is held.
    - `switchover` failing before `set_primary`: the hold is released and
      the old primary restarts (existing behavior). Write outage = time to
      abort + restart.
    - `failover` failing before `set_primary`: the old agent writes a fresh
      lease and restarts PostgreSQL as primary in the same epoch, after crash
      recovery. Write outage = time to abort + crash recovery.
    - a failure after `set_primary` leaves the cluster on the new primary (a
      normal HA state), marks the drill failed, and does not attempt
      failback.

### 5. Replica report policy
- **Sync standby:**
  - `hot_standby_feedback=off`, `max_standby_streaming_delay=30s`;
  - option `ro_use_sync_standby`, default `auto`:
    - the sync standby is excluded from the read-only listener when an async
      replica exists, so reports never slow commits or the failover target;
    - in a primary + sync-standby cluster, the sync standby serves reads with
      `max_standby_streaming_delay=30s`.
- **Async reporting replicas:**
  - `hot_standby_feedback=on`, `max_standby_streaming_delay=10min`;
  - while their replay lag exceeds `maximum_lag_on_failover` they are
    ineligible for automatic failover, which is the expected trade-off.
- **Lag-aware read-only listener:**
  - Option `ro_max_lag`, default `64MB` of replay lag (bytes).
  - It skips replicas beyond the limit.
  - If every replica exceeds it, it routes to the least-lagged replica and
    records a warning.
  - It routes reports to the primary only when `ro_fallback=primary` is set
    (default `none`, which rejects the connection when no replica is up).
- **S8 pass bar:**
  - reports of ≤10 minutes finish with 0 cancellations;
  - sync standby replay lag p99 ≤ 1s during reports;
  - primary dead-tuple growth during the run is recorded as a number, not
    gated.

## Reviewer Concerns

Disposition: CONCERNS_RECORDED

Stop: MAX_ITERATIONS

### R3-1 — feasibility (blocking)

**Problem**

> The lease carries the CLOCK_BOOTTIME value read 'at writing', not the time at which the renewal conditions (primary for the epoch, quorum confirmed, no monotonic gap) were last checked. If the agent is stalled between its check and the write (docker pause in S3, SIGSTOP, a long GC or scheduler stall, a slow disk), it writes a lease that looks fresh for a full lease_ttl after the stall, even though quorum was last confirmed long before. In S3 an agent frozen mid-renewal would, on unpause, publish a 7s-fresh lease before its next tick detects the gap, so the fence worker's 'first check sees the stale lease' claim and the timing bound do not hold.

**Remedy**

> Stamp the lease with the CLOCK_BOOTTIME time of the last quorum/role confirmation (the start of validity), not the write time, and have the agent refuse to write if that confirmation is older than Q. Then a stalled write can only publish an already-aged lease.

### R3-2 — clarity (blocking)

**Problem**

> The safety bound 'after the leader's last received heartbeat, the primary can renew for at most Q more' mixes events on different nodes. The follower's 2s window is measured from when it receives the acknowledgement, which comes after the leader received the heartbeat, so message and retransmit delays add to Q. The margin is only 0.5s (20s vs 19.5s). The timer origin is also undefined when the primary's agent was itself the Raft leader, or when leadership changes, because the new leader may never have received the old primary's heartbeats. Under those conditions, 'failover_timeout since that heartbeat' is not well defined and 20s >= 19.5s is not proven.

**Remedy**

> Measure the follower's renewal window from the send time of the acknowledged heartbeat (and of the /peer/info request) on the primary's own monotonic clock, and do the same for VerifyLeader. Define the new leader's failover timer origin as the later of the last heartbeat it received and the time it became leader. Restate the bound with that definition and keep an explicit margin.

### R3-3 — completeness (blocking)

**Problem**

> actual_sync explicitly includes standbys in `quorum` state, and automatic failover promotes 'only a member of the last committed actual_sync set'. With quorum commit (ANY k of n), any single member may lack commits that were acknowledged by the other members, so promoting an arbitrary member can lose acknowledged rows. The same applies to FIRST k with k > 1 if the most-advanced member is not chosen.

**Remedy**

> For quorum or multi-sync configurations, require the leader to see last good LSNs from at least n-k+1 members of actual_sync and promote the most advanced one. Otherwise block with failover_blocked. Alternatively, restrict this design to a single sync standby and say so. Add a scenario that covers it.

### R3-4 — completeness (blocking)

**Problem**

> In the failover drill the old primary's agent 'stays silent' (no heartbeats, no lease renewal), yet it must later learn either that promotion happened (so it resumes and rejoins) or that the drill aborted (so it restarts PostgreSQL as primary in the same epoch). The design does not say how a silent agent learns which outcome occurred, whether it stays a Raft member, or what happens if the primary's agent is itself the Raft leader that runs the drill. Restarting as primary without first confirming through Raft that no set_primary was committed and that no candidate was promoted risks two primaries.

**Remedy**

> Specify the drill's signaling: the old agent keeps reading Raft (or the leader sends drill_resume or drill_abort). Before restarting as primary, it confirms through a quorum read that the epoch is unchanged and no set_primary exists, then writes the lease under the normal renewal conditions. Before rejoining, it confirms that the new primary's epoch is committed. Say how the drill behaves when the primary's agent holds Raft leadership (for example, transfer leadership first).

### R3-5 — feasibility (minor)

**Problem**

> The fence worker is a PostgreSQL background worker. When the postmaster begins a fast shutdown it terminates background workers, so the worker cannot be relied on to send SIGQUIT 10s later. The 'up to 10s escalation' in the timing budget therefore has no working mechanism. Write safety still holds, because fast shutdown terminates backends and refuses new connections first. This carries R2-15 forward.

**Remedy**

> Do the escalation from a process that outlives the shutdown: a worker that ignores SIGTERM and exits last, or the agent's goroutine, with the dead-agent case stated. Alternatively, drop the escalation claim and state that safety rests on backends being terminated at the start of fast shutdown.

### R3-6 — clarity (minor)

**Problem**

> The design does not say how the cluster-wide fencing setting reaches each node's `worlber_ha.fence` GUC. Presumably each agent runs ALTER SYSTEM plus a reload, which needs a live agent on every node. It also does not say what happens on a node whose agent is down, or that a value persisted in postgresql.auto.conf stays off until fencing is turned back on. The GUC context (SIGHUP versus postmaster) is also not stated.

**Remedy**

> State the propagation path, the GUC context, and how fencing is restored after maintenance.

### R3-7 — scope (minor)

**Problem**

**Remedy**
